It is not a survey: each section is here because a later part needs it, and approaches to scalability are left to \autoref{ch:bg:scalability}.

Ethereum gets more space, because all three contributions target it: Part~II analyzes its transaction workload, Part~III designs state sharding for it, and Part~IV fits data availability sampling into its consensus.

The chapter goes from the general model to Ethereum's specifics.

It introduces blocks, hash chaining, Merkle trees, the roles that nodes play, and the full replication that limits throughput.

\section{Distributed Ledgers}\label{sec:bg:ledgers}

A distributed ledger is an append-only log of transactions, replicated by nodes that do not trust each other.
Bitcoin~\cite{nakamoto2008bitcoin}, launched in 2009, was the first such ledger to work in an open setting.
Its transactions transfer a native currency.
Ethereum~\cite{wood2014ethereum} followed in 2015 and let transactions call programs, smart contracts, whose code and storage live in the replicated state.
This section covers the parts of this model that the rest of the thesis uses; how nodes agree on the content of the log is left to \autoref{sec:bg:consensus}.

\paragraph{State machine replication.}
A ledger is a form of state machine replication~\cite{schneider1990smr}.
Each node holds a copy of a state $S$ (in the simplest case, the balance of every account), and a transaction $tx$ updates it through a transition function, $S' = \delta(S, tx)$.
Nodes that start from the same \emph{genesis} state $S_0$ and apply the same transactions $tx_1, \ldots, tx_n$ all end up with
\[
	S_n = \delta(\ldots\delta(\delta(S_0, tx_1), tx_2)\ldots, tx_n).
\]
This only works if $\delta$ is deterministic.
Smart contract execution environments (\autoref{sec:bg:execution}) are built around this requirement: programs get no local clock, no floating-point arithmetic and no access to external services, since any of these could give different results on different machines.
The state itself never needs to be exchanged, because any node can recompute it from the log.
Nodes only have to agree on the order of transactions, and that is the job of consensus.

\paragraph{Blocks and hash chaining.}
Transactions enter the log in batches called blocks.
A block has a body, the ordered list of its transactions, and a header with metadata: typically the hash of the parent header, a timestamp, and short commitments to the content of the block, such as the root of a Merkle tree over its transactions and, in some ledgers, a commitment to the state after the block is executed.

Since each header contains the hash of its parent, blocks form a hash chain back to genesis.
The idea predates blockchains and was first used to timestamp digital documents~\cite{haber1991timestamp}.
If the hash function is collision resistant, the most recent header fixes the whole history.
Altering a transaction in an old block changes that block's hash, hence the parent hash stored in its child, and so on up to the latest header.
Any node that knows a recent header sees the change.
Hash chaining, however, only makes a rewrite detectable.
Nothing stops an attacker from building a different chain that is internally consistent, and choosing among several valid chains is again a matter for consensus (\autoref{sec:bg:consensus}).

\paragraph{Merkle trees.}
The commitments in the header are usually roots of Merkle trees~\cite{merkle1987digital}.
Leaves are hashes of data items, and each inner node hashes its children, so the root depends on every leaf.
To prove that an item is in the tree, it is enough to give the sibling hashes on the path from its leaf to the root.
The proof grows logarithmically with the number of leaves, and anyone who knows the root can check it.
The state can be committed the same way.
When the header holds the root of a tree over all state entries (account balances, contract storage), any single entry can be proven against it.
How the state is laid out in practice depends on the transaction and state model of the ledger, the topic of \autoref{sec:bg:state-model}.

\paragraph{Permissioned and permissionless ledgers.}
Ledgers also differ in who maintains them.
In a permissioned ledger such as Hyperledger Fabric~\cite{androulaki2018hyperledger}, participants are known and authenticated in advance.
Classical Byzantine fault-tolerant protocols (\autoref{sec:bg:consensus:bft}) then apply directly, since they assume a fixed set of $n$ nodes of which at most $f$ are faulty.
Public blockchains such as Bitcoin are permissionless.
Anyone can join or leave, and an identity is just a public key, free to generate.
Nothing prevents one participant from creating many identities (a Sybil attack~\cite{douceur2002sybil}), so votes cannot be counted per identity.
Voting power is tied instead to a resource that is hard to obtain: computation in proof-of-work (\autoref{sec:bg:consensus:pow}), locked stake in proof-of-stake (\autoref{sec:bg:consensus:pos}).

We only consider permissionless ledgers in this thesis.
This constrains the mechanisms we add, namely the placement of state on shards in SOAPS (Part~III) and the assignment of data to nodes in PANDAS (Part~IV).
Both must work with open membership and with some participants acting maliciously.
Any node must be able to verify their outcome, and participants who would gain from a particular outcome must not be able to bias it.

\paragraph{Node roles.}
Nodes do not all do the same work~\cite{chatzigiannis2022sok}.
A full node checks each new block by re-executing its transactions and comparing the result with the commitments in the header.
It stores the current state, sometimes with a short window of recent ones.
Joining nodes rarely replay the chain from genesis.
They start from a recent checkpoint, download the matching state, and validate blocks from there; under proof-of-stake, the checkpoint must come from a trusted source, an issue tied to weak subjectivity (\autoref{sec:bg:consensus:pos}).
An archive node additionally keeps every historical state, so it can answer queries such as the balance of an account at some past block, at the cost of a much larger disk footprint.
Validators (miners under proof-of-work) are full nodes that also propose and vote on blocks; under proof-of-stake, they are the participants that have locked stake (\autoref{sec:bg:consensus:pos}).
At the other end, light clients follow only block headers and check individual values with Merkle proofs~\cite{chatzigiannis2022sok}.
They execute nothing and rely on most consensus participants being honest (\autoref{sec:bg:workload:light}).

\paragraph{Peer-to-peer network.}
Nodes form a peer-to-peer overlay in which each keeps a bounded number of connections.
Transactions and blocks spread by gossip: a node that receives a valid message forwards it to some of its neighbors~\cite{demers1987epidemic}.
Peers find each other through a discovery protocol, often a distributed hash table such as Kademlia~\cite{maymounkov2002kademlia}.
To keep bandwidth in check, practical gossip protocols push full messages to a few neighbors and only announce them, with short metadata, to the rest.

The network matters for security.
How fast blocks propagate bounds how fast they can be produced before security degrades~\cite{garay2015backbone,gervais2016security}, which is why block intervals are set well above the propagation delay.

\paragraph{Full replication.}
In the model so far, every full node stores the whole state and re-executes every transaction of every block.
No node has to trust another, but adding nodes adds no capacity.
Throughput is capped by what one node, run by an ordinary participant, can download, store and execute.
Larger or more frequent blocks would lift the cap, at a price.
Running a node would become more expensive, so fewer participants could afford it, and blocks would propagate more slowly, which means more forks and weaker security~\cite{gervais2016security}.
\autoref{ch:bg:scalability} discusses this problem and the main ways around it.
This thesis builds on one of them, sharding, where each node handles only a subset of the transactions and of the data.

\section{Consensus}\label{sec:bg:consensus}

Nodes that apply the same transactions in the same order reach the same state (\autoref{sec:bg:ledgers}).
A consensus protocol makes them agree on that order, block after block, even when some nodes are faulty or malicious and the network delays messages~\cite{lamport1982byzantine}.

\paragraph{Fault and network models.}
Blockchain consensus protocols generally assume \emph{Byzantine} faults: a faulty node may do anything.
It may stop responding, send wrong messages, collude with other faulty nodes, or \emph{equivocate}, i.e., send conflicting messages to different nodes, such as votes for two different blocks at the same height.
Assumptions about the network vary more.
The synchronous model guarantees delivery within a known bound $\Delta$.
The asynchronous model gives no bound at all, and Fischer, Lynch, and Paterson proved that in this model no deterministic protocol can guarantee agreement if even a single node may crash~\cite{fischer1985impossibility}.
Partial synchrony sits in between.
The network may be asynchronous for a while but eventually delivers messages within a bound, and agreement is then possible with fewer than a third of Byzantine nodes~\cite{dwork1988partial}.
Longest-chain protocols assume synchrony~\cite{garay2015backbone}; most BFT protocols target partial synchrony~\cite{castro1999pbft,yin2019hotstuff}.

\paragraph{Safety and liveness.}
Two properties are expected from consensus.
\emph{Safety} means that honest nodes never confirm two conflicting blocks, so a confirmed transaction is never reverted.
\emph{Liveness} means that the protocol keeps making progress, so a valid transaction from an honest client is eventually included.
When the network can be partitioned, the two pull against each other.
A protocol that keeps producing blocks on both sides of a partition cannot also promise that those blocks never conflict.
One answer is to run two layers: a chain that keeps growing under any conditions, and a slower finality mechanism that confirms a prefix of it only once enough participants agree~\cite{neu2021ebb}.
Ethereum is built this way (\autoref{sec:bg:eth-pos}).

\paragraph{Sybil resistance.}
Because votes in a permissionless ledger are weighted by a costly resource and not counted per identity (\autoref{sec:bg:ledgers}), security assumptions are stated in terms of that resource: honest participants hold a majority of the computing power in proof-of-work (\autoref{sec:bg:consensus:pow}), or a majority of the stake in proof-of-stake, more than two thirds when finality comes from a BFT-style vote as in Ethereum (\autoref{sec:bg:consensus:pos}).
Classical BFT protocols (\autoref{sec:bg:consensus:bft}) offer no Sybil resistance on their own.
In practice they are often run on top of proof-of-stake, by a committee chosen according to stake.

\subsection{BFT Variants}\label{sec:bg:consensus:bft}

Classical Byzantine fault-tolerant (BFT) protocols, from PBFT~\cite{castro1999pbft} onward, assume a fixed, known set of $n$ nodes, at most $f$ of them Byzantine, with $n \geq 3f+1$.
Decisions need a \emph{quorum} of $2f+1$ nodes.
Two quorums overlap in at least $f+1$ nodes, hence in at least one honest node, and an honest node never votes for two conflicting values.
Two conflicting decisions can thus never both reach a quorum.
In PBFT, a leader proposes a value and the nodes agree on it in three phases: pre-prepare, prepare, and commit.
A faulty or slow leader is replaced through a \emph{view change}~\cite{castro1999pbft}.
Unlike in longest-chain protocols, finality is immediate: a decision is never reverted as long as the bound on $f$ holds.

The cost is communication.
PBFT has every node send its votes to every other node, $O(n^2)$ messages per decision, which in practice limits the number of participants.
HotStuff~\cite{yin2019hotstuff} brings this down to $O(n)$: the leader collects the votes and combines them into one threshold signature.
Aggregatable signatures such as BLS~\cite{boneh2001short,boneh2003aggregate} serve the same purpose, turning thousands of votes into a single signature checked in one operation.

Sharded blockchains such as OmniLedger~\cite{omniLedger} and RapidChain~\cite{rapidchain} run a BFT protocol inside each shard, among the committee assigned to it.
Committee size is then a trade-off.
Small committees agree faster, but they are more likely, by chance, to have more than a third of malicious members.
\autoref{sec:bg:sharding} comes back to this.

\subsection{Proof-of-Work}\label{sec:bg:consensus:pow}

Proof-of-work was first proposed against spam, as a small computation required for each email~\cite{dwork1992pricing}.
Bitcoin turned it into a way to elect who appends the next block~\cite{nakamoto2008bitcoin}.
A miner produces a valid block by finding a nonce for which the hash of the block header falls below a target.
No shortcut is known, so miners try values one by one, and the chance of finding the next block is proportional to one's share of the total computing power.
The target is adjusted periodically to keep the block rate roughly constant, at one block every ten minutes on average in Bitcoin.

When two miners find a block at nearly the same time, the chain splits into two branches, or \emph{forks}.
A \emph{fork-choice rule} decides which branch to follow.
Bitcoin's is the longest chain rule (more precisely, the chain with the most accumulated work), and miners build on the branch it selects.
GHOST~\cite{sompolinsky2015ghost} follows the heaviest subtree instead.
Blocks on discarded branches then still count, and the protocol stays secure at higher block rates.
Proof-of-stake fork-choice rules later built on this idea (\autoref{sec:bg:eth-pos:forkchoice}).

Finality under these rules is only probabilistic.
A heavier branch can always revert a block, but the probability drops exponentially with the number of blocks on top of it, hence the usual advice to wait for several confirmations.
The Bitcoin backbone analysis~\cite{garay2015backbone} proves the protocol secure when honest miners hold a majority of the computing power and blocks propagate quickly relative to the block interval.
Larger or more frequent blocks cause more forks, and the work spent on discarded branches no longer protects the chain~\cite{gervais2016security}.
Throughput cannot simply be raised by tuning these parameters, and \autoref{ch:bg:scalability} starts from this observation.
Proof-of-work is also energy-hungry, since security grows with the computation miners spend.

\subsection{Proof-of-Stake}\label{sec:bg:consensus:pos}

In proof-of-stake, participants called \emph{validators} lock an amount of currency, their \emph{stake}, and their weight in the protocol is proportional to it.
They earn rewards for proposing blocks and voting correctly.
Ouroboros~\cite{kiayias2017ouroboros} and Algorand~\cite{gilad2017algorand} both come with formal security proofs, but take different routes.
Ouroboros keeps a longest-chain structure and picks block producers according to stake.
Algorand draws small committees by cryptographic sortition, and each committee decides on a block with a Byzantine agreement protocol.

Since the protocol holds the stake, it can punish misbehavior directly.
A validator that equivocates, for instance by signing two different blocks for the same position, produces two signed messages that together prove the fault and identify who committed it~\cite{sheng2021forensics}.
Anyone can put this proof in a block, and the protocol then destroys part of the validator's stake.
This is called \emph{slashing}.
Security rests on economics: an attack needs a large share of the stake and puts that stake at risk.
SOAPS (Part~III) relies on rewards and slashing, and \autoref{sec:bg:eth-pos:safeguards} describes how Ethereum implements them.

At each step, a proof-of-stake protocol must pick the proposer of the next block and the committees that vote on it, using randomness produced by the protocol itself~\cite{gilad2017algorand}.
If this randomness is predictable long in advance, attackers can prepare against the selected nodes.
If participants can influence it, they can steer the selection toward positions that benefit them, and this has been shown to work in practice~\cite{nagy2025forking}. \mat{CHECK: that Nagy et al.\ show the manipulation in practice (on mainnet) and not only in principle.}
SOAPS and PANDAS inherit the problem, since both assign tasks to nodes from this randomness (\autoref{sec:bg:eth-pos:committees}).

Two further problems are specific to proof-of-stake.
Signing a block costs nothing, so a validator could vote on every competing branch; slashing exists to rule out this \emph{nothing-at-stake} behavior.
Slashing has a blind spot, though.
Once validators have withdrawn, their old keys can still sign an alternative history from far in the past (a \emph{long-range attack}).
A node joining the network cannot tell such a history from the real one using the genesis block alone, and needs a recent checkpoint from a source it trusts, an assumption called \emph{weak subjectivity}.

\section{Ethereum Proof-of-Stake}\label{sec:bg:eth-pos}

All three contributions target Ethereum, and two of them depend directly on its consensus.
SOAPS (Part~III) builds on its committees and penalties, and PANDAS (Part~IV) must fit in the timing of its slots.
This section goes into more detail than \autoref{sec:bg:consensus} for that reason.
Unless stated otherwise, parameters come from the consensus specifications~\cite{ethconsensusspecs}.

Ethereum launched with proof-of-work and moved to proof-of-stake in September 2022, in the upgrade known as \emph{the Merge}.
Since then, an Ethereum node runs two programs.
The \emph{consensus client} runs the \emph{beacon chain}: it manages the validator set, assigns validators to committees, and decides which blocks belong to the chain and which are final~\cite{schwarzschilling2022three}.
The \emph{execution client} holds the state and the pool of pending transactions, and executes the transactions of each block in the Ethereum Virtual Machine (\autoref{sec:bg:execution:evm}).
The two talk over a local interface, the Engine API, through which the consensus client asks the execution client to build or check the \emph{execution payload}, the list of transactions carried by a beacon block.
The beacon chain itself is inherited from earlier sharding designs, where it was meant to coordinate many shard chains (\autoref{sec:bg:sharding}).
The system model of SOAPS follows that original design.

\subsection{Validators}\label{sec:bg:eth-pos:validators}

Becoming a validator requires a deposit of at least 32\,ETH in a deposit contract and running both a consensus and an execution client.
Each validator has an \emph{effective balance}, derived from its actual balance, which sets its voting weight and its chance of being picked as proposer or aggregator.
Until the Pectra upgrade in May 2025, the effective balance was capped at 32\,ETH, which forced large stakeholders to run many validators.
Pectra raised the cap to 2048\,ETH for validators that opt into compounding withdrawal credentials, so stake can now be consolidated into fewer validators.
Stake remains concentrated all the same: staking pools and liquid staking services control a large share of it, spread over many separate validators.

Validators have three regular duties.
When selected as the proposer of a slot, they propose a block.
Once per epoch, they \emph{attest}, i.e., they sign a vote on the current head of the chain and on the latest checkpoints (\autoref{sec:bg:eth-pos:committees}).
Some are also chosen as aggregators and combine the attestations of their committee into one signature.
Since the Altair upgrade, there is also a \emph{sync committee} of 512 validators, renewed every 256 epochs (about 27 hours), which signs each block header.
Light clients can then follow the chain without tracking the whole validator set (\autoref{sec:bg:workload:light}).

Validators enter and leave the active set through queues.
A \emph{churn limit} bounds how many can be activated or exit per epoch.
The validator set cannot change too quickly, and in particular an attacker cannot gain a large weight in a short time.
The active set is on the order of a million validators. \mat{CHECK: current number of active validators at submission (consolidation since Pectra lowers it).}
At this scale, a classical BFT protocol in which every validator exchanges votes with every other (\autoref{sec:bg:consensus:bft}) is out of the question.
Ethereum relies instead on committees and signature aggregation, described below.

\subsection{Slots and Epochs}\label{sec:bg:eth-pos:slots}

Time is divided into \emph{slots} of 12 seconds, and 32 slots make an \emph{epoch} of 6.4 minutes (\autoref{fig:bg:eth-slot}).
Each slot has a single proposer, which may publish one block.
If it does not, the slot stays empty.

Proposers are drawn at random, weighted by effective balance, from a value called the RANDAO mix.
Every proposer includes in its block a signature over the current epoch number, and this signature is mixed into the RANDAO value.
The mix at the end of an epoch seeds the selection of proposers and committees for a later epoch.
A proposer cannot choose its contribution, since its signature is fixed in advance.
It can withhold its block, though, and its contribution is then skipped.
The last proposers of an epoch can exploit this to pick among several possible seeds and bias future proposer selection in their favor~\cite{nagy2025forking}.
The selection is also public before the slots it concerns.
Nodes can prepare, but so can an attacker, who knows which node to target at what time (e.g., with a denial-of-service attack).

Each slot follows a fixed schedule.
At 0\,s, the proposer publishes its block, which then propagates through the network.
The validators in the committee of the slot attest to the head of the chain as soon as they have received and validated the block, and at the latest at 4\,s.
At 8\,s, aggregators publish the aggregated attestations of their committee.
A validator thus has at most 4 seconds to receive and check a block before voting. \mat{CHECK: slot timing at submission (enshrined PBS and shorter-slot proposals may change the 12\,s / 4\,s schedule).}
If the block arrives late or cannot be checked in time, the validator votes for the previous head, and the block will likely be left out of the chain.
In PANDAS (Part~IV), validators must also verify that the data attached to the block is available, and this check has to fit in the same 4 seconds.

\subsection{Committees and Attestations}\label{sec:bg:eth-pos:committees}

At each epoch, the active validators are shuffled with the RANDAO seed and split into committees.
Each slot gets between 1 and 64 committees, and each validator sits in exactly one committee per epoch, so it attests exactly once per epoch.
When there are enough validators, the shuffle keeps every committee at or above 128 members, above the minimum of 111 recommended for committee safety.
With around a million validators, committees are in fact several times larger, with several hundred members each.

The shuffle is deterministic and uses only public data, the seed and the list of active validators.
Any node can recompute the committees and check that an attestation comes from a member of the right one, without trusting anybody.
Our two designs reuse this pattern of a deterministic function of public randomness that any node can recompute.
SOAPS uses it to elect the validator that computes the placement of state on shards, and the witnesses that check it; PANDAS uses it to decide which node is responsible for which part of the data.

An attestation carries three votes.
The \emph{head vote} names the block that the validator sees as the head of the chain, and feeds the LMD-GHOST fork-choice rule.
The \emph{source} and \emph{target} votes name two checkpoints, and feed the Casper FFG finality mechanism~\cite{schwarzschilling2022three}.
Attestations use BLS signatures~\cite{boneh2001short}, which can be aggregated~\cite{boneh2003aggregate}: the signatures of all committee members who cast the same vote collapse into one, with a bit field recording who signed.
Without aggregation, about a million signatures per epoch would have to go into blocks, more than the bandwidth of nodes can carry.

\subsection{Fork-Choice Rule}\label{sec:bg:eth-pos:forkchoice}

The consensus protocol of Ethereum, Gasper, combines two mechanisms~\cite{schwarzschilling2022three,neu2021ebb}.
LMD-GHOST, a fork-choice rule, selects the head of the chain and lets it grow even when many validators are offline.
Casper FFG, a finality mechanism, runs on top of this chain and finalizes some of its blocks.
This is the ebb-and-flow structure of \autoref{sec:bg:consensus}: the chain selected by LMD-GHOST stays available, while the finalized prefix stays safe under network partitions~\cite{neu2021ebb}.

LMD-GHOST adapts GHOST (\autoref{sec:bg:consensus:pow}) to votes.
Starting from the latest justified checkpoint, it follows at each fork the branch whose subtree carries the most weight, counting only the latest attestation of each validator (hence \emph{latest message driven}).

Casper FFG reasons in epochs, and the checkpoint of an epoch is the block at its first slot.
Once validators holding at least two thirds of the stake attest with the same source and target, the target checkpoint is \emph{justified}.
A justified checkpoint is \emph{finalized} when the checkpoint of the next epoch is justified with it as source.
Under normal conditions, a block is final after two to three epochs, about 13 to 19 minutes.
Reverting a finalized block would mean finalizing two conflicting checkpoints.
That takes at least a third of the stake signing contradictory votes, which can be proven and slashed (\autoref{sec:bg:eth-pos:safeguards}).

The fork-choice rule has been attacked in several ways.
In a balancing attack, a few Byzantine validators time the release of their votes so that honest validators stay split between two branches~\cite{neu2021ebb}.
In an ex-ante reorganization, the attacker withholds a block and its votes, and releases them later to outweigh the next honest block~\cite{schwarzschilling2022three}.
The protocol now counters both with \emph{proposer boost}.
A block received on time, before the 4\,s mark, gets extra weight in the fork choice until the end of the slot, equal to 40\% of the weight of a committee.

Validators should vote only for blocks that are valid and whose data is \emph{available}, meaning that anyone can download it.
With Data Availability Sampling (\autoref{sec:bg:l2:limitations}), they check availability by downloading a few random samples of the data rather than all of it.
The \emph{tight} fork-choice rule has them run this check before attesting, so a block whose data cannot be retrieved never becomes the head, however valid it is otherwise.
The \emph{trailing} rule runs the check later.
Validators get more time, but the guarantee is weaker, since others may build on a block before its data has been checked~\cite{damato2024dasforkchoice}.
PANDAS targets the tight rule, which is why sampling must finish within the first 4 seconds of the slot~\cite{pigaglio2025pandas}.

\subsection{Rewards and Safeguards}\label{sec:bg:eth-pos:safeguards}

Validators are paid for performing their duties correctly and on time, and lose a little when they miss them.
The reward for an attestation depends on which of its three votes are correct and on how quickly it was included in a block.
Proposers earn rewards for including attestations and evidence of misbehavior, and sync committee members for signing headers.

A validator is \emph{slashed} for signing messages that contradict each other: two different blocks for the same slot, two attestations with the same target epoch but different content, or an attestation whose source and target surround those of another of its own~\cite{schwarzschilling2022three}.
The proposer that includes the resulting proof (\autoref{sec:bg:consensus:pos}) receives a reward.
The slashed validator immediately loses 1/4096 of its effective balance, is forced to exit, and can withdraw what remains only after 8192 epochs, about 36 days.
Halfway through this period, it pays a \emph{correlation penalty}: the fraction of the total stake slashed in the same window, multiplied by three, is taken from its balance, up to the whole of it.
A one-off fault, usually a misconfiguration, costs little.
A coordinated attack by a third of the stake costs the attackers all of it.

Another safeguard covers the case where finality stops.
With more than a third of the stake offline, no checkpoint can gather two thirds of the votes, and the chain stops finalizing.
After four epochs without finality, the \emph{inactivity leak} kicks in.
Validators that do not participate lose balance at an increasing rate, until those still active again hold two thirds of the stake and finality resumes.
The leak has to be designed with care: Pavloff et al.\ show that Byzantine validators can use it to drain the stake of honest validators and raise their own relative weight~\cite{pavloff2024byzantine}.

Ethereum, then, does not prevent misbehavior.
It punishes it whenever it can be proven and attributed to a validator.
SOAPS relies on these same mechanisms (election, stake, and slashing) instead of adding a consensus protocol of its own.
Every deviation from SOAPS must therefore be detectable and attributable to a specific validator, which is the purpose of its challenge mechanism.

Finally, the block of a slot is often not built by its proposer.
The order of transactions in a block can be profitable, for example when one's own transaction is placed just before or after a large trade.
This profit is called \emph{maximal extractable value} (MEV)~\cite{daian2020flashboys}.
Capturing it takes specialized infrastructure, and Ethereum has adopted, outside the protocol, a form of \emph{proposer-builder separation} (PBS).
\emph{Builders} assemble blocks and bid for them to be proposed; \emph{relays} pass the highest bid to the proposer, which signs the header without seeing the content.
A handful of builders produce most blocks~\cite{heimbach2023pbs}.
For PANDAS, this means that the data to distribute and sample starts at a few well-connected, well-provisioned builders, while most of the nodes sampling it run on modest hardware.

\section{Transaction and State Models}\label{sec:bg:state-model}

The state machine view of \autoref{sec:bg:ledgers} says nothing about what the state contains, or how a transaction designates the part of it that it reads and modifies.
That is the role of the state model.
It defines which data a transaction accesses, and so when two transactions conflict, which in turn governs whether they can run in parallel (\autoref{sec:bg:workload:parallel}) and how the state can be split between shards (\autoref{sec:bg:sharding:state}).
Bitcoin introduced the \emph{unspent transaction output} (UTXO) model~\cite{nakamoto2008bitcoin}, in which the state is a set of coins.
Ethereum uses the \emph{account-based} model~\cite{wood2014ethereum}, in which it is a set of accounts with balances and storage.
We work with accounts throughout, but start with UTXOs, because the contrast explains several difficulties that Parts~II and~III deal with.

\subsection{UTXO Model}\label{sec:bg:state-model:utxo}

In the UTXO model, the state is the set of transaction outputs not yet spent.
An output holds an amount and a spending condition, usually a signature from the key of its owner.
A transaction consumes existing outputs, its \emph{inputs}, and creates new ones.
Each input names the output it spends, by the identifier of the transaction that created it and its index there, and supplies the data that satisfies the spending condition.
Outputs cannot exceed inputs in total, and the difference goes to the block producer as a fee (\autoref{fig:bg:utxo}).
An output can be spent only once.
Two transactions spending the same output form a \emph{double spend}, and at most one of them makes it into the ledger.

\begin{figure}[t]
	\centering
	\input{figures/utxo_tx.tex}
	\caption{A transaction in the UTXO model.
		It consumes two outputs owned by Alice, which are removed from the set of unspent outputs, and creates two new ones: a payment to Bob and the change returned to Alice.
		The difference between inputs and outputs is the fee.}
	\label{fig:bg:utxo}
\end{figure}

Because inputs are listed in the transaction, the state a transaction depends on is known before it runs.
Two transactions conflict only if they spend the same output, or if one spends an output that the other creates.
Transactions with no outputs in common can be validated in parallel.
A sharded design can place each output on a shard, say by the identifier of the transaction that created it, and know in advance which shards a transaction touches.
Several of the first sharded blockchains were built on UTXOs for this reason~\cite{omniLedger,rapidchain}, and transaction placement methods have been proposed for the model~\cite{Nguyen2019}.

The catch is that outputs are consumed whole and hold no persistent data.
Applications with shared, long-lived state, such as a token or an exchange used by many users, are hard to express.
Extended UTXO models attach data and more expressive scripts to outputs while keeping explicit inputs, but the application still has to split its state into outputs that are consumed and recreated on every update~\cite{chakravarty2020eutxo}.
The workloads we study and the systems we target use accounts, so we leave UTXOs aside from here on.

\subsection{Account-Based Model}\label{sec:bg:state-model:account}

In the account-based model, the state maps addresses to accounts.
Ethereum has two kinds of accounts.
\emph{Externally owned accounts} (EOA) are controlled by a private key and hold a balance and a \emph{nonce}, the number of transactions the account has sent.
Every transaction carries the nonce of its sender.
This forces the transactions of an account to execute in order, and keeps a signed transaction from being replayed.
\emph{Smart contract accounts} (SCA) are created by deploying code.
Besides a balance and a nonce, they hold that code and a persistent \emph{storage}: a mapping from 256-bit keys, called slots, to 256-bit values, which only the code of the contract can modify (\autoref{sec:bg:execution}).
A token contract typically keeps the balance of each holder in its own storage slot.

Transactions are sent by EOAs.
A transaction transfers currency to another account, deploys a new contract, or calls an existing one with some input data.
The called contract may call others, which may call others again, so one transaction can read and modify many accounts and storage slots.
Only the original transaction appears in the block.
The \emph{internal transactions} it triggers can only be observed by executing it (\autoref{sec:bg:execution:evm})~\cite{pigaglio2023exploring}.
Activity is also very uneven: a small number of accounts, such as exchanges, popular token contracts and decentralized finance protocols, take part in a large share of all transactions~\cite{guo2019graph}.

The key difference from UTXOs is that the state a transaction will access is not known in advance.
It depends on the code of the contracts involved and on the current contents of their storage, which may change between the moment the transaction is signed and the moment it runs.
The same call can touch different slots, or even different contracts, depending on what executed before it.
Whether two transactions conflict, i.e., whether one writes data that the other reads or writes, is generally known only after both have run.
Ethereum does let a transaction declare an \emph{access list} of the accounts and slots it plans to use~\cite{eip2930}.
The list is optional, though, and the transaction may still touch state it did not list.
This makes parallel execution (\autoref{sec:bg:workload:parallel}) and state sharding (\autoref{sec:bg:sharding:state}) harder with accounts than with UTXOs.
Part~II measures how real transactions spread their accesses over time and across one another, and the same uncertainty complicates the placement of accounts in SOAPS (Part~III).

Executing a transaction costs \emph{gas}.
Each operation of the execution environment has a fixed gas cost reflecting the resources it uses, and storage reads and writes are among the most expensive.
The sender sets a maximum amount of gas and pays for the gas actually used.
Since the London upgrade, the gas price has two parts~\cite{eip1559,roughgarden2021tfm}.
A \emph{base fee}, set by the protocol, rises when blocks are fuller than a target, falls when they are emptier, and is burned.
A \emph{priority fee}, chosen by the sender, goes to the proposer.
When demand is high, it decides which transactions get in first, and so how long a transaction waits to be included~\cite{pacheco2023my}.
Each block also has a \emph{gas limit} that bounds its total computation, and this limit is, in effect, the throughput of the chain.
It is kept low enough for nodes on modest hardware to execute a block within a slot, a direct consequence of full replication (\autoref{sec:bg:ledgers}).

\section{Smart Contracts and Execution Environments}\label{sec:bg:execution}

A \emph{smart contract} is a program stored in the ledger and executed by every full node whenever a transaction calls it.
Its state, such as balances or open positions, is part of the replicated state, and only the code of the contract can modify it.
All nodes run the same code on the same state and get the same result, so nobody has to be trusted to execute the contract correctly.

Much of the activity on Ethereum goes through a few kinds of contracts.
Token contracts record who owns which units of a fungible asset (the ERC-20 interface) or which non-fungible items (ERC-721).
Around them sit decentralized exchanges, which let users swap one token for another against liquidity pools held by a contract, lending protocols, which lend tokens against collateral, and bridges, which lock assets on one chain to release equivalent assets on another.
In the workload analyzed in Part~II, transactions involving contracts took over as time went on, and simple transfers, which made up more than 80\% of early transactions, fell to around 20\% by the Merge~\cite{pigaglio2023exploring}.

Contracts call each other, and applications are often assembled from existing contracts.
A swap on a decentralized exchange may go through a router contract, then through one or more pools, each calling the token contracts of the assets it holds, so a single transaction can end up involving tens of contracts.
Even the simplified two-step swap of \autoref{fig:bg:calltree} involves six.

	\caption{Calls made by a transaction in which Alice swaps token X for token Z through two exchange pools (X to Y in Pool A, then Y to Z in Pool B).
		Only the transaction from Alice to the router is recorded in the block.

These calls are what create dependencies between accounts in the account-based model (\autoref{sec:bg:state-model:account}).
They also explain why some contracts, widely used tokens and exchange pools in particular, are accessed by a large fraction of all transactions.
Such contracts turn into contention points as soon as transactions run in parallel or the state is split between shards.

\subsection{The Ethereum Virtual Machine}\label{sec:bg:execution:evm}

Ethereum contracts run on the Ethereum Virtual Machine (EVM)~\cite{wood2014ethereum}, a stack machine that operates on 256-bit words.
During a call, a contract sees a stack, a temporary \emph{memory} discarded when the call ends, the input data of the call, and its persistent \emph{storage} (\autoref{sec:bg:state-model:account}).
Every instruction costs gas, and execution aborts with an error when the gas of the transaction runs out, so every execution terminates.
Storage accesses are by far the most expensive instructions.
Reading a slot for the first time in a transaction costs hundreds of times more than an arithmetic operation, and writing a slot that was previously zero costs more still, because each such operation reads or updates the state database of every node.

A contract calls another with \texttt{CALL}, which runs the code of the callee on the storage of the callee.
\texttt{STATICCALL} does the same but forbids any change to the state.
\texttt{DELEGATECALL} runs the code of the callee on the storage of the caller, which is how libraries and upgradable contracts work.
When a call fails, its changes to the state are reverted, and the caller is free to continue and handle the failure.
Transactions in a block run one after the other, in the order chosen by the block producer, each seeing the state left by the previous one.

The state is stored in Merkle Patricia Tries, which combine the Merkle trees of \autoref{sec:bg:ledgers} with a prefix tree (Patricia trie), so that each key determines a unique path from the root to its value.
There are two levels.
The \emph{world-state trie} maps the hash of each address to its account: nonce, balance, code hash, and storage root.
Each contract has its own \emph{storage trie}, which maps the hash of each slot to its value.
The root of the world-state trie is the state root found in each block header.
Reading a value means walking from the root down to a leaf, which may take several disk accesses.
Because keys are hashed, entries that belong together in the application, two slots of the same contract for instance, land in unrelated parts of the trie and of the disk.
State access is one of the main costs of executing a block, and clients cut it down with caches and flat copies of the latest state.
Those caches only pay off if transactions tend to access state that was accessed recently, a property called temporal locality (\autoref{sec:bg:workload}).

The block alone does not reveal the read and write sets of a transaction, since internal transactions are not recorded in it (\autoref{sec:bg:state-model:account}).
To get them, we replay the whole chain with the Go Ethereum (geth) client and record, for every transaction, the accounts it reads and writes, including those touched by its internal transactions (\autoref{fig:bg:calltree}).
Replaying the chain up to the Merge takes about three days and yields a dataset of about 2\,TB; Part~II describes the tool we built to process it~\cite{pigaglio2023exploring}.

Sequential execution over a single global state, together with a gas limit that keeps execution within reach of modest nodes (\autoref{sec:bg:state-model:account}), puts a hard cap on the throughput of Ethereum.
In October 2026, the gas limit is 60 million gas per block~\cite{etherscangaslimit}. \mat{CHECK: gas limit and average tx/s at submission; update the derived 2{,}850 tx/block and 240\,tx/s.}
The cheapest transaction, a plain transfer, costs 21{,}000 gas~\cite{wood2014ethereum}, so a 12-second slot holds at most about 2{,}850 transactions, or under 240\,tx/s.
Real transactions use far more gas, and the chain processes around 20\,tx/s on average~\cite{etherscantx}.

\subsection{Alternative Execution Environments}\label{sec:bg:execution:alternatives}

Many other blockchains reuse the EVM, as do most layer-2 protocols (\autoref{sec:bg:l2}).
EVM compatibility lets them run existing contracts and reuse the same development tools, and their workloads tend to look like that of Ethereum, because they host the same kinds of applications.
Chains with other virtual machines, for example based on WebAssembly, usually keep the same model of contracts executed sequentially over shared state.

Another line of work changes the execution model itself to allow parallel execution.
Dickerson et al.\ proposed that block producers execute contract calls speculatively in parallel and publish the resulting schedule, so that validators can replay the block in parallel and deterministically~\cite{dickerson2017concurrency}.
Several recent blockchains were designed for parallel execution from the start.
Solana has each transaction declare the accounts it will read and write, and runs in parallel the transactions whose accounts do not overlap~\cite{yakovenko2019sealevel}.
Sui models the state as objects, and separates objects owned by a single user from shared ones.
Transactions that use only owned objects need no ordering relative to others and skip consensus; only those on shared objects go through it~\cite{blackshear2024sui}.
Aptos uses Block-STM, which runs the transactions of a block optimistically in parallel, detects conflicts at runtime, and re-executes the transactions involved, giving the same result as a sequential execution in block order~\cite{gelashvili2023blockstm}.

These designs take one of two approaches.
Either transactions declare their dependencies up front, which comes naturally with UTXOs but constrains how contracts are written with accounts, or the system executes optimistically and bets on conflicts being rare.
Either way, the gain depends on the workload, since transactions that access the same accounts still have to run one after the other.
\autoref{sec:bg:workload} returns to these techniques.
